# Bank Reconciliation Agent

A rules-first, tool-calling agent that matches New Zealand small-business bank lines to invoices on a synthetic ledger. Deterministic rules close the lines with one obvious answer. For the rest, the agent searches and proposes matches through four narrow tools, code verifies every proposal, a shadow policy decides which ones a human must see, and nothing is posted without that. **The model never does arithmetic and never writes to the books.** Every number below is regenerated from `results/*.json` by one command, and CI fails if they drift.

## How it works

```
bank line ──► rules pass ──► closed: exact amount, one candidate, payer or reference agrees
                 │
                 └─► agent, one conversation per line
                        search_candidates    open invoices, relation to the line computed in code
                        find_combinations    2 or 3 invoices of one payer that add up exactly
                        propose_match        checked by the verifier before it is queued
                        escalate             to a human
                 ──► shadow policy ──► review queue ──► a person approves or rejects ──► posted
```

- **Rules pass** ([rules.py](src/recon/rules.py)). Closes a line only when exactly one open invoice has the amount and the payer name or the reference agrees. It reads the bank-written fields and never the memo. Run alone, it is the baseline.
- **Agent** ([agent.py](src/recon/agent.py)). A loop of about 150 lines, one isolated conversation per bank line, with step, token and cost limits. It ends only on a terminal tool; a text answer, a truncated reply, conflicting final calls, a provider error or a limit all become escalations.
- **Tools and verifier** ([tools.py](src/recon/tools.py)). Strict JSON schemas. Sums, differences and the fee tolerance are computed in code, so the model only chooses. A proposal may cite only invoices that the search returned for that line, must belong to the payer on the line unless the reference names the invoice, must add up, and a part payment must be named in the remittance text.
- **Shadow policy** ([policy.py](src/recon/policy.py)). Auto-approves only the boring case: one invoice, the exact amount, at most NZ$1,000, a payer already matched correctly, payer text that does not read like an instruction. Owner bank rules auto-approve inside a sign and size envelope. In shadow mode it records verdicts and posts nothing.
- **Review** ([db.py](src/recon/db.py)). A reviewer role approves or rejects each queued proposal. Every decision writes an append-only audit row; allocations carry amounts, and a part payment leaves its invoice open.
- **Postgres with least privilege** ([schema.sql](src/recon/schema.sql)). The agent's role can read the ledger and insert proposals, nothing else. It cannot read the evaluation labels. A trigger makes the audit table append-only, even for the owner.

### Why a hand-rolled loop

The loop is short enough to read in one sitting, and every way it can end is a line of code with a test. Approvals, budgets, escalation on every non-terminal ending, replay keyed by request and tracing are all things this project needs to control exactly, so an agent framework would add surface without removing work. The tool calls go through one OpenAI-compatible client, which keeps the provider a configuration choice.

### Provider-agnostic

DeepSeek, Ollama, Gemini, OpenAI and Anthropic all serve the OpenAI Chat Completions format, so a provider is one row in [llm.py](src/recon/llm.py): base URL, key variable, model id and prices. The results above use DeepSeek's hosted model; a local `gpt-oss:20b` row runs through Ollama. Only synthetic data is ever sent to a provider.

## Security

The bank memo is written by whoever paid, so it is the injection surface. The design assumes the model will sometimes be fooled and puts the controls in code. [docs/threat-model.md](docs/threat-model.md) maps each threat to OWASP LLM Top 10 (2025) and to the control and test that cover it.

- Payer text is fenced as data, and the prompt says it is never an instruction.
- Personal data (NZ IRD numbers with their check digit, bank accounts, phones, emails) is removed before any request and again from rationales. Every planted value is searched for in every outbound request.
- The verifier refuses another payer's invoice, sums that do not add up and invoices the search never returned.
- There is no posting tool, and the database role could not post if there were.
- The policy screen keeps instruction-like text away from auto-approval. It is a keyword screen built from the development business only; the held-out business shows how little it generalises, which is why it is not the control that matters.

The safety and ablation tables above measure these layers separately.

## Where this breaks

- **The data is synthetic and the scores show it.** Both businesses come from one generator, so the held-out business tests new seeds, invoice formats, wording and case mix, not new kinds of mess. Real bank feeds have reversals, multi-currency lines, batch deposits and payers who never quote a reference.
- **The injections are templated.** Each goal has a few fixed phrasings, attached to an otherwise ordinary memo. A payload written to read like a normal remittance, or spread across reference and memo, is not measured yet. The verifier and the human gate are the defence for those, by design.
- **The keyword screen does not generalise.** See the held-out column of the safety table.
- **Small counts give wide bounds.** A zero out of a few dozen lines is reported with its upper bound for that reason.
- **One model so far.** The local model row and a second hosted model are the next measurements.
- **Replay tests the harness, not the model.** The CI gate replays recorded model output; it proves the code still makes the same decisions from the same answers. Live quality comes only from the dated results files.

## Verification

- `tests/test_synth.py` checks every label with an oracle written apart from the generator: no second invoice, combination or fee-window candidate fits any line. A fingerprint pins the ground truth.
- `tests/test_db.py` runs against Postgres: the agent role cannot write the ledger or read labels, the audit table refuses updates, deletes and truncation, the rules pass makes no wrong match, no attack lands on a line the rules close, and every labelled answer clears the verifier's payer check.
- `tests/test_gate.py` replays a committed 40-line slice through the whole pipeline and requires the same rules decisions, agent decisions and policy verdicts as the recording, no new wrong match or successful attack, no leaked personal data, and no provider error. A doctored copy of the cassette must fail.
- `tests/test_report.py` fails if the results block in this README differs from what `recon report` writes from `results/*.json`.
- Every results file records the commit, marked dirty if the code differed from it, the prompt hash, the model settings and the dataset fingerprint.

## Run

Needs [uv](https://docs.astral.sh/uv/) and Docker. Copy `.env.example` to `.env` for the model keys.

```bash
make db          # Postgres 17 with pgvector and pg_trgm on localhost:5433
make test        # unit tests, least-privilege tests, the replay gate, the README check
make demo        # offline: replays the committed 40-line slice, no key needed
make baseline    # the rules pass alone, on both businesses
make eval        # live, three repeats per business; writes results/*.json
uv run recon report   # rewrite the results block above from results/*.json
```

A run leaves its proposals in the review queue. The policy runs in shadow mode: it records what it would auto-approve and posts nothing. A person reviews the rest:

```bash
uv run recon review list --run <run id>
uv run recon review approve <proposal id> --note "checked remittance"
uv run recon review reject <proposal id> --note "unknown payer"
```

## How this was built

The rules the coding agents work under are committed in [AGENTS.md](AGENTS.md). Independent reviews ran after each milestone; the mistakes they caught, and what changed because of them, are in [docs/agent-log.md](docs/agent-log.md).

> **Synthetic data only.** Every business, contact, invoice and bank line is generated from a seed. No real customer, accounting-platform, tax-authority or employer data is used. Personal-data values are random strings in real NZ formats, tied to no real name. This is a portfolio project, not accounting advice.
